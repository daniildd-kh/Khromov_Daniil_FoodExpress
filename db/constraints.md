## Общие технические решения

- Все ID сущностей и FK имеют тип UUID, PK сущностей получают default `exts.uuid_generate_v4()` по BR-11.1
- Внешний `payment.transaction_id` хранится текстом, так как по BR-8.3 приходит от провайдера и не является генерируемым PK нашей сущности
- Составные PK связей и выплаты сохранены из ERD, год и месяц не являются полями ID
- Все обязательные атрибуты имеют NOT NULL по BR-11.3, исключения перечислены ниже
- Пустые и состоящие только из пробелов обязательные имена, логины, описания и телефоны отвергаются CHECK, это техническое прочтение BR-11.3/11.4
- Текстовые лимиты 20, 24, 64, 100, 128, 150 символов выбраны по назначению поля согласно BR-11.6, не являются дополнительными бизнес-правилами
- Цены и денежные суммы имеют два десятичных знака, количество три, рейтинг агрегата четыре, коэффициент один
- Время событий хранится в timestamptz и группируется в часовом поясе сервера по BR-11.2
- Все восемь списков статусов реализованы CREATE TYPE AS ENUM по BR-11.5 и соответствующим BR-4.3, 5.5, 6.2, 7.7, 7.9, 8.2, 9.1
- В FK нет ON DELETE CASCADE, родительская строка с историческими зависимостями не удаляется автоматически
- Тексты ограничений не вводят города, скидки, карты, возвраты или дополнительные сущности бизнеса вне раздела 12

## Индексы

Частичный уникальный индекс успешного платежа обеспечивает целостность
Неуникальные индексы доставленных заказов, блюд ресторана и объектов отзывов ускоряют ожидаемые соединения
Они не заменяют корректную агрегацию, FOOD-106 не умножает суммы заказов на число позиций

## Генератор и отчёты

Генератор добавляет новый независимый набор и не очищает существующие строки
На один `value` приходятся одна запись в client, courier, product_category, restaurant, пять в address, product, orders, review, payment, четыре связи client_address, пять позиций и шесть выплат
Строки и даты создаются только внутри учебных диапазонов, первый курьер принудительно активен
Семь выбираемых enum-наборов берутся через enum_range, статус оплаты заказа вычисляется из платежей

Начальный исторический коэффициент 0.1, выплаты формируются хронологически за шесть календарных месяцев
После генерации коэффициент работающего курьера соответствует следующему месяцу
Повтор зарплаты использует сохранённый коэффициент месяца, уволенному следующий коэффициент не назначается

get_statistic отдельно агрегирует суммы заказов, количество блюд и частоту клиентов
Для равных лидеров используется random, best_user содержит логин по FOOD-106 и BR-2.6
how_much_money строит непрерывный ряд месяцев рекурсивным CTE и использует LAG

## Решения по неоднозначным требованиям

- ERD требует прямые связи `review` с клиентом и заказом. `client_id` уже определяется по `order_id`, поэтому его хранение является исключением из строгой 3НФ. Для совместимости с исходной схемой поле сохранено, составной внешний ключ исключает расхождение с владельцем заказа
- Комиссия и итог заказа вычисляются PostgreSQL из `order_amount`. Рейтинги хранятся как агрегаты, которые обновляет триггер по отзывам
- До успешной оплаты заказ может иметь ноль успешных попыток, а после первой успешной попытки вторую блокирует частичный уникальный индекс. Так одновременно учитываются BR-8.1 и состояния оплаты из BR-8.7
- Для истории выплат берутся шесть календарных месяцев, включая текущий. Зарплата и финансовый отчёт используют время доставки, а повторный расчёт месяца берёт сохранённый коэффициент `coefficient_used`
- В отчёте месяцы без доставок имеют нулевую выручку и комиссию. Если в таком месяце вручную внесена выплата, она входит в расчёт по формуле `net_profit = commission - courier_pay`
- Дамп содержит определения объектов только `khromov_food`. Расширение `uuid-ossp` в `exts` готовится отдельно по BR-13.3
